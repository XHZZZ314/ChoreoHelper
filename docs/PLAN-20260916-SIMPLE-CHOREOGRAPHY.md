# 单人和多人共用的简洁编舞流程方案

日期：2026-09-16。面向产品所有者；状态：已核对当前源码的详细方案，尚未实施。
需求登记：`INT-20260916-SIMPLE-CHOREOGRAPHY`。本次只新增方案、需求登记和连续性指针，不安装、不操作游戏、不改变现有项目或素材。

## 1. 最终要交付什么

用户只需要会选择人物、选择动作和编舞。无论一个人还是八个人，都走同一条流程：

**安装并打开 → 添加演员 → 选音乐、编动作和走位 → 网页排练 → 游戏合练 → 保存或交给其他演员。**

普通用户不需要知道骨骼、动画包、转换器、资源路径、角色档案标识等技术概念。默认流程禁止要求用户改文件、运行脚本、手工绑骨骼、逐个录动作或逐个修转换失败。录制只保留为高级可选功能，不能成为原生动作预览的必经步骤。

单人与多人使用同一种项目、人物卡片、素材准备、播放器和操作。增加一个演员，就是增加一条演员轨道，不另开一套工作流。

第一轮完整交付验收为 1/4/8 位演员。已有更大项目仍保留，但不能把未测过的人数宣传为稳定支持。

## 2. “一次性处理好”究竟怎么做

可以做批量准备，而且应该做。这里的“一次”是对**同一份实际素材和同一版本转换规则**而言，不是每个项目、每个演员各来一次；游戏内容变更、转换规则修正时只更新受影响部分。

### 2.1 不要把三个东西混在一起

| 内容 | 白话说明 | 准备和复用方式 |
|---|---|---|
| 动作目录 | 有哪些动作、叫什么、属于哪个职业 | 统一读取和更新；目录有名字不代表已有动画 |
| 原始动作和播放结构 | 身体怎样动，前摇、循环、结束怎样接 | 相同文件及动画条目只解码一次；不同技能仍保留自己的时间结构 |
| 身体匹配规则 | 游戏怎样把动画用于某种身体 | 对应骨骼组合的规则验证后复用；不为每个角色手写规则 |
| 人物外观 | 脸、衣服、发型、武器和模型 | 每套外观准备一次；外观变化不应让所有公共动作重做 |

职业用于筛选技能、确定武器/动作变体和游戏执行条件，不应成为复制整套动作库的理由。角色档案仍分别保存，公共资源在底层共享；“共享文件”不等于“把甲的私人档案绑定给乙”。

游戏提供同一个动作的种族/性别专用版本时自动选专用版本；游戏共用动画时使用其经过验证的匹配规则。禁止以骨数相同、名称相似或职业相同推断兼容，禁止拿其他种族动作冒充。

### 2.2 两种准备范围，用户不用研究

**默认：自动优先准备当前需要的内容。** 首次使用先准备所选人物和演示/当前项目所需动作；连接可用时选入新动作自动加入队列，已经准备过的直接播放。普通编舞中不要求用户逐条点“准备”。

**可选：一次备齐全部受支持原生素材。** 设置中提供“准备完整离线动作库”：自动识别本机游戏版本，扫描已声明支持的可用玩家身体变体和动作，去重、转换、验证、保存。先展示实测/估算磁盘需求，再开始；支持暂停、退出续做和取消。任务完成后，新建项目、换职业、添加已覆盖种族都直接复用。

两者使用同一个队列和资料库，只改变任务优先级/范围，不产生两套格式。默认先让用户尽快开始编舞；需要完全离线自由选动作的用户只需点一次全量准备。

“完整”必须带明确范围：当前游戏版本、支持的玩家种族/性别/身体变体、普通动作和职业技能清单。NPC、坐骑、特殊变身等不同体系单独列范围，不混进分母也不悄悄承诺。若范围内仍有不支持项，显示“已准备 X 项，Y 项暂不支持”，不能报“全部完成”。

### 2.3 不要预先展开所有组合

不把“每个演员 × 每个职业 × 每个动作”都保存一份。保存去重后的源动画、匹配规则和播放结构；目标身体第一次需要的结果自动生成并缓存。全量离线准备需同时备齐所声明身体所需规则与依赖，使以后离线也能自动完成必要适配。

推荐初期继续使用现有播放器可接收的已适配动作，采用按需生成和有上限缓存；不要立即重写为实时通用骨骼计算。是否预生成更多结果，由实际耗时和空间数据决定。

一次全量准备不承诺“几秒处理完”。开发先量出资源数、解码耗时、内存和磁盘需求，界面据此显示进度和预计剩余时间。

## 3. 当前源码的事实，以及必须补的缺口

本节为 2026-09-16 源码核查结果；历史验证仅作已有证据，本次未重新跑浏览器、资源转换或游戏验收。

| 当前事实 | 对方案的影响 |
|---|---|
| `src/CharacterAnimationBindings.cs` 主要读取当前本地人物已绑定资源；所选文件必须已绑定，还有限量检查 | 不是全游戏、全种族动画索引；不能靠切换每种角色、让玩家放遍技能来完成全量准备 |
| `src/SkillResourceReader.cs` 按 Action 读取动画时间线及引用 | 读取目录/引用，不等于所有对应动画已经成功解码 |
| `scripts/local-skill-assets/prepare_bound_actions.py` 已能批量处理并按源文件复用解码结果 | 复用现有成果，但目前仍以捕获清单和具体目标人物为输入 |
| 同一脚本限制源骨架代码，要求单一可读执行时间线，并对咏唱、多条动画引用等结构拒绝或要求另行组合 | 把这些提升为通用结构支持，不能只不断添加新的技能编号特例 |
| `prepare_motion.py` 支持已实现的局部映射，明确拒绝链式映射 | 游戏有匹配数据，不等于软件已经实现全部规则；缺规则由开发补实现和验证 |
| 转换器经固定路径、固定哈希的私人工具链调用 | 不能直接交付普通用户；需封装受支持的安装、依赖检查和进程隔离；分发条件待核实 |
| `web/choreo-skill-motion.js` 核对真实 Action、来源、目标档案/骨架和映射证据 | 新共享资源层必须保留这些校验，不以“通用缓存”绕过人物隔离 |
| `web/choreo-model-import.js` 仍需要当前/已绑定档案的骨架，再验证所导模型 | 任意其他种族模型不能直接保证无条件自动导入；须补自动识别和骨架获取 |
| 已有模型文件夹导入、角色包、资料库、多人物预览、时间轴和离线缓存 | 扩展现有链路，不重建播放器、音乐时钟或项目中心 |
| `web/choreo-ensemble-*.js` 已有双人直连接入及其他协同组件 | 旧设计文档的“未实现”说明已落后；先审现有接线和实测，不另造多人系统 |

已记录的技能预览、离线恢复成功是有限角色/资源的证明，不作为全目录、全种族完成证明。

## 4. 从安装到完成一场舞：用户真正看到的流程

### 4.1 安装与首次打开

目标入口为受支持启动器中的插件安装/更新入口；正式发布前保留自用安装路径，但公开交付不能要求手工复制 DLL 或网页目录。

首次打开只解释三件事：连接自己的游戏、添加演员、打开示例或新建项目。插件已有“打开编舞”入口，继续复用。可信连接能否进一步减少手输配对步骤，须在现有配对安全边界内验证，不能简单删除配对。

本地网页文件仍是完整可用入口，不把核心使用强制迁到在线网站。游戏未启动也能打开已准备项目。提供可用示例；新安装 30 秒进入示例是验收目标，不是当前已达成声明。

安装包含网页与受支持准备组件，自动检查缺失/版本问题。新用户不安装 Python、不找转换器路径、不设置环境变量。转换组件是否可随包分发、是否能替代为可维护实现，是开发前置检查；若解决不了，不得把安装步骤转嫁给用户后宣布完成。

### 4.2 添加演员

人物入口只呈现“我的游戏人物”“已有角色”“导入角色包”。每张卡片显示名字、缩略图、当前编排职业和就绪状态；技术档案隐藏在高级诊断。

“我的游戏人物”的最终目标是一次明确点击后，自动取得当前外观与身份并入库。**当前尚无已验证的完整网格导出能力，不能先写一个按钮就算完成。** 首包需验证可维护的本地导出集成；已有 Meddle 路径作为兼容入口，不能长期成为新人必须掌握的外部技术步骤。

若外观集成暂时受阻，允许明确选择符合该身体身份的简化预览继续编舞，同时标明“未导入真实外观”；这只能是过渡体验，不能宣称人物一键准备完成，更不能换用其他种族动作。没有正确身体数据时只显示缺失，不伪装兼容。

朋友只需导入别人给的一个角色包；软件自动校验、预览并用于选中演员。重复包以真实身份/内容判断，不按名字合并。多个候选模型才让用户选缩略图，不能让用户选骨骼文件。

同一个人物可保存多个外观；改衣服不清空编舞、不重复准备兼容的公共动作。切换种族或身体后自动重算资源需求；不静默替换原人物。

### 4.3 选音乐、编舞

选本地歌曲；添加演员动作、技能、走位、朝向；沿用时间轴、复制、多选、撤销、音乐节拍和歌词/台词能力。所有编辑即时保存。

动作列表默认按当前演员/当前段职业筛选；可主动查看其他职业作为草稿。网页允许排练不代表游戏一定能释放；不能因为模拟冷却或技能条件未知就禁止用户编舞。

普通动作、技能都由同一素材准备服务提供动画。新增动作自动准备；八个人用同一素材只建一个公共任务，不发生八次解码。职业切换采用已有显式编排，不擅自插入换装或游戏指令；实际装备套装由该玩家在合练时选择一次。

### 4.4 网页排练

点击播放，所有演员按各自轨道同时表演；同种族可做不同动作，不同种族也可做同一动作的正确版本。沿用同一个播放时间和音乐时钟，支持暂停、拖动时间轴、倍速排练和片段反复检查。

上方只给简明提示：“可以排练”“正在准备 3 个动作”“小明有 1 个动作暂不支持”。问题可以直接定位到人物和片段；详细原因进入高级诊断。

缺失内容不阻止用户编辑或查看其他人物；如选择继续排练，受影响片段明确标为未显示，不能悄悄用另一个动作/人物代替。网页身体动作与游戏 VFX 分开，网页不承诺还原技能特效。

准备任务在后台完成不得突然改当前播放中的版本或暂停姿势；完成后更新就绪提示，在确定的暂停/重播边界采用新资源。用户切项目后，旧任务仍可填充公共缓存，但不得改新项目、人物绑定或播放状态。

### 4.5 离线继续

资源就绪后显式显示“本项目可离线排练”。这句话必须检查本场所有人物、动作、时间结构和音乐；缺歌曲时提示重新选原文件或明确选择本次无音乐排练。

离线新加入的动作若源素材和匹配规则均已缓存，自动完成准备；依赖缺失时保留编排，说明“连接游戏后会自动补齐”。不能承诺未缓存资源在离线时凭空可用。

退出浏览器、重启电脑、关闭游戏、网络断开后均应可以恢复已完成资源。不得只验证断网标签或仅刷新页面。

### 4.6 游戏合练

统一“去游戏合练”入口：单人只有本人，多人列出演员及各自准备状态，不分裂成两套项目。

每位玩家首次认领自己的演员，检查当前人物、职业/装备套装、支持事件、起点和朝向；确认后记住这份关联。换人/换项目/修改演出后重新检查对应信息，不要求每次重建素材。

所有玩家各自明确点准备，开始前呈现倒数和统一开始时刻；网络断开、晚到或未准备的人不能被自动拉入正在进行的演出。停止入口始终可见，每个客户端只控制自己。离线网页排练与多人网络合练明确区分。

第一步实机贯通一个人的整场，再验证双人，最后八人；复用现有协同代码、ShowRunner 和本地输出控制。技能到点尝试一次，游戏拒绝则记录并继续既定后续事件，不自动补放、追赶或重试。网页拖时间轴不补发游戏技能。

结束报告按演员、时刻说明“做了什么/被拒绝/结果无法确认”；接口返回成功不能显示为已看到实际动作或特效。

### 4.7 保存、分享、换电脑

对外只给两个主要选项：“保存编舞”和“打包带走”。前者保存已有项目；后者汇总项目及需要的人物、动作和音乐，清楚说明包含范围/大小并让用户确认音乐是否打包。

“打包带走”是新的外层封装，优先复用现有项目和角色包内容，不另造第二套内部编舞模型。完整打包若缺素材必须先提示，不允许生成缺依赖的包却宣称完整。

导入先检查，再原子写入；失败不污染现有库。优先复用已有相同内容，保留人物身份和显式映射，导入同名人物也不乱绑。旧项目、旧备份和私人录制必须继续可读。

## 5. 一次准备如何在内部落地

本节给后续开发执行，技术内容不进入普通用户操作界面。

### 5.1 可发现的完整资源关系

建立本地游戏版本对应的关系：动作/技能真实 ID → 播放阶段和引用 → 原始动画条目 → 身体/武器/姿态变体 → 所需骨骼与原生匹配规则。

首要技术验证是：能否从本机已安装游戏数据解析未加载到当前人物的资源和正确变体，而不要求用户登录每种种族或逐个播放技能。现有当前人物绑定读取接口不能直接承担这个任务。

复用游戏数据读取基础；新能力必须有明确资源范围、版本能力标识、分页/大小限制和只读边界。扫描不输出动作、不改变人物、不自动换职业。不能把当前接口简单改成任意路径文件下载器。

若有运行时才能确定的映射，先划清其覆盖范围并研究确定性的解析方法；确需普通使用时观察的可做无输出的自动观察，但不能把“用户逐个执行动作以收集资源”当全量方案。无法解决的范围记为开发缺口，影响完整交付。

### 5.2 公共资源与个人资料分开

建议新增内部共享资源层，保留现有人物档案和项目引用边界。资源主存放在稳定的本地应用目录，浏览器保留离线工作副本；插件不可用时不影响已有离线副本使用。两者有一致性校验和版本清单，不依赖浏览器永远不清缓存。

建议缓存身份至少包含：

- 源动画：源文件内容哈希、包内动画条目/绑定、源骨骼内容、解码器版本。不能只有技能 ID 或 PAP 文件哈希。
- 匹配规则：源/目标骨骼内容、完整规则内容与版本、必要身体变体。
- 播放结构：动作类型及 ID、动画变体、各阶段时间线和依赖哈希。共用动画的两个技能也不能把时长/阶段合并掉。
- 生成结果：源动画身份、目标骨骼、匹配规则、播放器格式版本。
- 外观：模型与依赖文件内容、蒙皮/骨架身份、必要外观版本。

游戏版本作为索引和追溯上下文；是否重算由实际内容及算法版本决定，不能更新一次游戏就全库作废。原生基础资源与本机修改素材隔离，不能只靠一个“有修改”布尔值复用所有人物数据。

公共动画的目标身份校验采用显式适配层交给当前播放器；禁止删除现有 profileId/skeletonHash 验证，也禁止将旧人物专属录制直接提升为通用资源。资料库升级需新版本及迁移测试，迁移失败保留旧库可用。

### 5.3 通用动画结构支持

按结构而非技能编号开发：普通单次、持续循环、起始/循环/结束、咏唱/施放、多个执行动画、必要局部身体层与混合、根节点位移、武器及附属骨架、特殊体型。

先建立真实样本清单与拒绝原因，分清直接可复用和需新增实现的类别。不能以单条动画成功代表整个技能已还原；不能将咏唱固定时长误当游戏实时咏唱；根节点动作与舞台世界坐标移动必须分开，防止移动两次。

每种原生匹配结构只实现一次；静态参考姿势对齐只是首道检查，还需动态关节、坐标轴、旋转、比例和阶段衔接验证。所有支持组合跑结构检查，真实视觉验收覆盖每个不同规则族/身体变体及复杂阶段，不要求用户自己对拍每个动作。

### 5.4 准备队列和失败处理

优先级：当前选中动作 → 当前演出 → 用户选择的完整离线库。限制并发、内存和磁盘，不在游戏主线程执行长时间解码；已有只允许游戏线程获取的元数据应短时获取，再交后台工作。

同一资源任务合并，多项目引用只计一次工作；断电/中断保留完成项；先写临时结果、验证后原子提交。失败单项不撤销整个库、不静默采用半成品。

用户只看到准备进度、暂停/继续、磁盘不足和简短原因。确定性不支持不无限重试；短暂连接失败允许有限退避的只读准备重试，永不带出游戏动作。连接恢复时继续剩余素材，游戏演出本身绝不自动重开。

### 5.5 更新和恢复

游戏或软件更新后先快速检查版本，再按索引找变化；旧缓存仍可用于明确标记的旧版本网页排练，但不把旧版资源或历史准备结果当作当前游戏执行许可。

更新结果完整后再切换，失败继续保留旧版本；不覆盖私人模型、用户录制和旧项目。浏览器缓存被清理后能从本机主库恢复；换电脑则使用打包带走/备份。清理缓存前区分可重建公共数据和用户独有资产，后者不自动删。

### 7.2 性能和正确性不能靠感觉汇报

记录测试机器、游戏版本、浏览器、模型复杂度、人数、资源规模、冷热缓存。分别量首轮准备耗时、重复准备任务数、缓存体积、动作选中到首个正确姿势、时间轴交互延迟、帧耗时和持续内存。

## 8. 硬性约束和未决技术问题

已明确的产品决策：统一单人/多人流程；本地优先；自动匹配；公共资源批量复用；录制非必需；真实种族动作；不要求普通用户处理技术文件；沿用当前播放器/时钟/数据；不做账号、云素材库或遥控他人客户端。

待开发验证而非丢给用户选择的问题：

1. 全种族/全部所声明玩家动作的确定性离线资源解析覆盖率，哪些规则还缺实现。
2. 原生链式映射、多层/多阶段、武器/附属骨架的准确处理范围。
3. 可维护、可安装的人物外观获取方式；Meddle 集成有无可用接口，不能预设存在。
4. 现有转换工具的可分发性、依赖、失败隔离与维护方案；不直接复制私人环境。
5. 全量准备的磁盘/耗时规模和浏览器离线副本策略。
6. 现有双人协同到八人的实际接线、网络适用范围和误差上限。

每项都要有验证结果和下一步，不把“未知”永久放在用户面前。若影响产品目标而暂时不可解，报告具体缺口，不能缩减目标却称完整交付。

个人模型、动作、项目只保存在本地；软件包只包含可分发程序与合规演示资产，不把所有者的游戏提取数据或私人模型打进公共安装包。新 HTTP 私有读取/批量任务需要能力版本、方法/来源/配对检查和边界测试。方案并不授权创建远程资源、发布、安装覆盖或新实机输出。
